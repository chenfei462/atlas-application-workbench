# Atlas database and private file backups

For the Chinese quick start and the distinction between database/files and browser drafts/briefs, see the [repository README](../../README.md#数据存在哪里). Windows users can use the root `备份Atlas.cmd` for a preserved manual bundle. Browser writing briefs and unsaved essay drafts must be exported separately; no database backup contains them.

Run `npm run backup` for a daily bundle with seven-successful-bundle retention, or `node scripts/backup.mjs` for a preserved manual bundle. No prompts or password printing. A new timestamp/UUID directory under `backups/` contains `database.dump` (custom pg_dump, public/auth/storage schemas, data, functions, triggers and policies), `atlas-export.json` (portable normalized schemaVersion 3, explicit 500-row pages), private file bytes under `storage/<bucket>/<logical path>` and `manifest.json`. Supabase CLI status supplies local admin credentials in memory; never put them in source or reports. Backups contain sensitive applicant data and auth hashes: protect the directory with restricted OS permissions and encrypted disk/offline copies.

Every database/export/file entry records filename, byte size and SHA-256. Manifest records backup ID, timestamp, source origin, migration head and status, plus sorted complete function/trigger definitions, policy roles/commands/conditions and table RLS enabled/forced states for public and storage schemas. Each object records bucket, logical path, owner, material/version IDs, source metadata/version, size, timestamp, checksum and status. Verification validates schema3 JSON, all 30 required normalized tables, unique row IDs, every file reference and object entry, the binary PGDMP header, exact public table/auth-user archive inventory via `pg_restore --list`, and full archive decoding to `/dev/null` (no SQL execution). A matching checksum alone is insufficient. A missing reference, failed download, invalid path, source change, failed dump or failed export gives FAIL and a nonzero exit. A FAIL bundle must not be used as a valid backup. Keep writes quiet during a backup: storage and database cannot share one atomic snapshot. The script rereads normalized rows, storage inventory and exact schema definitions to detect concurrent changes.

`npm run backup:integrity` checks the live formal database and storage inventory without deleting or repairing anything; `node scripts/integrity.mjs --bundle backups/<id>` checks a bundle. The report lists missing database references and unreferenced objects. Material files, submission receipts and import archive storage paths all count as valid references. Orphan objects are reported, never deleted.

Install the daily Windows task in one command: `powershell -NoProfile -File scripts/install-backup-task.ps1 -At 03:00`. It runs as the current user, starts a missed run when available, forbids overlapping scheduled runs, logs to `backups/logs/` and returns the Node process exit status. Inspect Last Run Result in Task Scheduler. Docker Desktop and the source local stack must be running; an offline stack fails visibly. To remove the schedule: `Unregister-ScheduledTask -TaskName Atlas-Daily-Logical-Backup -Confirm:$false`. On another platform, schedule the same `node scripts/backup.mjs --daily` command from the checkout root using that platform's scheduler and verify its behavior separately. Scheduling is optional and must be installed explicitly.

Only daily PASS bundles passing the complete structural, reference, checksum and archive validation are eligible for retention. Keep the latest seven; preserve manual bundles, failed/partial bundles, older incomplete manifest formats and unrecognized directories. Cleanup validates real paths under the workspace backup root, rejects symlinks and handles cross-volume Windows paths. A sole verified successful copy is never deleted.

Run `npm run backup:restore-test` for a real fresh restore drill. The script creates only a random fake user and chain in the source stack, backs it up, and deletes only that user's data/files after copying. It generates a separate `work/backup-test-stack/supabase` config and copies the current migrations. API 55431, database 55432 (55442 if 55432 is already occupied), mail 55434 and pooler 55439 isolate it from API 55421. Existing unrelated containers are never stopped to free a port. The main stack is never reset. `node scripts/restore-test.mjs --bundle backups/<id> --credentials work/backup-test-credentials-<id>.json` restores an existing valid bundle into a fresh drill directory; it does not create or delete source fixtures and works without the original source database. File/hash/schema/credential preflight precedes target startup; archive validation uses the new target container. For an interrupted startup with an empty generated stack, add `--resume`; restore refuses existing auth/public rows and requires the target migration head to match the source exactly.

The restore checks all bundle checksums, applies migrations as schema source of truth and copies the repository's schema-only seed helper (`seed_demo_data`; it does not execute demo inserts), restores public rows plus auth users/identities atomically using the isolated database's `supabase_admin` role, restores private bytes through the Storage API and preserves ownership. Trusted isolated local restore temporarily disables SQL triggers during data load; RLS stays enabled. Do not reuse this procedure against an existing or production database. Full archive retains other auth data for disaster recovery, but the drill restores users/identities only, deliberately omitting obsolete sessions/tokens and migration tables. Restore compares every normalized row, table counts, every public foreign key through actual anti-join queries, file SHA-256, exact public/storage function and trigger definitions, full policy roles/commands/conditions and RLS enabled/forced flags, then requires the matching backed-up owner's real password login. Fixtures include a PDF referenced by both a material version and a submission receipt, plus a real JSON import archive referenced by `import_batches.archive_path`. `work/backup-test-restore-report.json` records RESTORE_PASS/FAIL; no RESTORE_PASS is emitted without successful login. Generated private credentials contain backupId and owner ID and stay in ignored `work/backup-test-credentials.json` plus a per-bundle private copy. Missing, stale or unrelated credentials fail. For a manual bundle, provide a private credential file with `backupId`, `id`, `email`, `password`, or securely set all four environment variables `ATLAS_RESTORE_BACKUP_ID`, `ATLAS_RESTORE_OWNER_ID`, `ATLAS_RESTORE_EMAIL`, `ATLAS_RESTORE_PASSWORD`; never put passwords on the command line or in reports. To repeat comparisons after an interrupted verification, use `--bundle backups/<id> --credentials <private-file> --resume --verify-only`; this uses only the target stack and performs no row/file restoration or source cleanup. The frontend must still confirm that the restored account can load its records and download its files.

The restore stack remains running for frontend smoke testing. After inspection, stop only that stack using the pinned CLI with `--workdir work/backup-test-stack`; archive the generated drill directory before another run. Never use `db reset` on the main local project. For external disaster recovery use migrations plus verified archive and file bytes with compatible Supabase versions, and validate auth, ownership, RLS and bucket policies before use.
